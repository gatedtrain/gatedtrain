# Multi-framework, multi-modality prototype: specification

- See the [design references](README.md#design-references) for rule IDs and the [recipe path mapping](README.md#unpublished-references).
- **Scope (maintainers' decision, 2026-11-11):** 8 areas, 9 runs, one GPU (an RTX 4090, 24 GB). GPU hours are logged in `<HOST_WORK>/gpu-log.md` and every full run is preceded by a smoke; the launcher passes `GATEDTRAIN_GPU_CAP_H=1000` to the operator's `gpu-step.sh` wrapper as a budget ceiling high enough not to limit runs. The runs are a controlled prototype under design R10-11.
- **Design sources (revision 10):**
  - 05 §3.1, §3.3-§3.8 (gates), §6.1 (independence, scorer validity), §11-§12 (lineage, precision, `ConsumptionRecord`), §14 (seeds);
  - 02 §2.4 (cut and completion manifests), §7 (lineage identity);
  - 08 §2.4 (wrapping an external library, M5), §3 (family notes), §6.1-§6.2 (environment versions, normalizer as policy state);
  - 06 B18 and §10 (code-executing environments).
- **Builds on:** `MVP-SPEC.md`, `TIER-B-SPEC.md`, `gatedtrain/tierb.py` (`merge_eval`, `collect`), `gates.py`, `ledger.py`, `impact.py`, `runner.py`, `report.py`, `registration.py`, `canonical.py`. The design revision 10 alignment of `gatedtrain` (R10-3/5/8/9/10: power, null-hash refusal, `max_unpaired`, `post_hoc` and amendments, `min_paired`, shuffle check, actual-K check, p-values, orphaned counts) is assumed merged. This spec calls those checks; it never re-implements them.
- **Goal:** for each of the 9 runs, go from a framework's own outputs to the same run directory, lockfile, ledger, gate report and impact answer that `tierb-collect` gives, through one generic command and one small adapter per framework. Model quality is not the point (decision, "Goal").
- Adapter tests run on CPU using recorded or synthetic outputs, with no training framework imports.
- **Not in scope:** changing any framework's source, the run contract (02 §2), hooks, signing. Every artifact is tagged `prototype` and `unpromotable`.
- **Notation:** "estimate" marks an unmeasured number; "unverified" marks a fact not yet checked against a pinned clone (check it in the adapter's smoke run and cite file:line in the adapter module).

## 1. Per-item evaluation record

An evaluator adapter writes one **arm directory** per evaluated checkpoint: `items.jsonl` plus `eval_meta.json`.

- **MM-1 Line schema.** Each line of `items.jsonl` is one (item, repeat):

  | Field | Type | Rule |
  |---|---|---|
  | `item` | string (any hashable ID in the library) | Key from the registered item set (MM-6); never a row index |
  | `repeat` | int | 0 ≤ repeat < K |
  | `seed` | int | Equals `registration.clause.eval_seeds[repeat]` |
  | `score` | finite number or null | Deciding metric in **natural units** (WER as WER, not negated) |
  | `error` | null or `{class, message}` | Evaluator-infrastructure failure only (MM-4); `score` is null iff `error` is non-null |
  | `sub_metrics` | object of finite numbers or null | Optional, descriptive only, never gated |
  | `output_ref` | null or `{path, sha256}` | Generated output (image, video, transcript, CAD code, episode log) relative to the arm directory; no component is a symbolic link (hard links are allowed); opened component by component without following links, and collect copies the bytes it checked |
  | `item_meta` | object or null | Optional, for example `{task, init_state}`; not used for pairing |

  Unknown top-level keys are refused (no silent schema drift).
- **MM-2 Arm metadata.** `eval_meta.json` (canonical JSON) holds: `schema: gatedtrain.item_eval`, `schema_version: 1.0`, `evaluator_id`, `adapter`, `metric` (name), `direction` (`higher_is_better` or `lower_is_better`), `score_range` (`[lo, hi]`, either bound may be null for unbounded), `checkpoint` (the `model_hash` of MM-17 that was evaluated, plus `base_model_hash` for LoRA), `normalizer_sha256` (embodied, else null), `env_version_sha256` (env items, else null), `item_set_hash`, `eval_seeds`, `sampler` (resolved deployment sampler, 05 §3.3) and its `sampler_hash`, `scorer` (`{name, version, weights_sha256 or null, code_sha256}`), `framework` (name and version used to generate). Wall-clock fields are excluded from every hash.
- **MM-3 Direction and range come from the adapter registry, not from the arm.** `ext-collect` refuses an arm whose `metric`, `direction`, `score_range` or `scorer` differ from the registered evaluator's entry, or whose any `score` lies outside `score_range` (generalizes decision D-11 beyond [0, 1]).
- **MM-4 Policy failure is a score, evaluator failure is an error.** Each adapter declares, in its registry entry, which outcomes are scores (the model's fault: CAD code that does not execute, a drone crash, an empty transcript) and which are errors (the evaluator's fault: scorer raised, simulator process died, OCR model failed to load). An error record is an unpaired item with reason `error:<class>`; it counts against `pairing.max_unpaired` (05 §3.4) and the report lists counts and reasons per arm. With the default bound 0, any error refuses, as decision D-3 does for Tier B.
- **MM-5 Merge.** `gatedtrain ext-merge-eval --registration R --out DIR RUN...` merges single-seed or multi-seed arm directories into one arm. It refuses when: a run is missing or empty; the union does not cover each registered seed exactly once; a run's `seed` disagrees with its repeat; item sets differ between repeats; `checkpoint`, `scorer`, `sampler_hash`, `normalizer_sha256` or `env_version_sha256` differ between runs; `--out` exists. Repeats are relabelled by registered seed order (G-16 semantics), and `merge.json` records each source's path, sha256 and seeds, as `merge_eval` does. `ext-collect` checks an arm's sources, and re-derives its `items.jsonl` from them, only when `merge.json` exists; an arm written in one piece with K repeats has no `merge.json`, and its provenance is the evaluator's claim (tests/README.md EXT-47, EXT-52).
- **MM-6 Item set.** The spec's gate input `items` (artifact type `item_set`; design revision 11, tests/README.md section 11.16) is a directory holding `items.jsonl` with unique `item`s (plus the payload the evaluator needs: prompt text, audio path and hash, episode seed, `(task, init_state)`). Its manifest hash must equal `registration.eval_distribution.item_set_hash`. Every record's `item` must be in the set; a record whose `item` is not makes the clause MISSING (`unknown_item`, design 05 §3.8 revision 11), with the run written (exit 1), not a refusal (maintainers' decision 2026-11-11); set items without a usable record in an arm are missing items with reason `absent` (05 §3.4, `gates.evaluate_items`).
- **MM-7 Pairing.** Pairs are keyed by `(item, repeat)`. The records go to `gates.evaluate_items` as they are (scores in natural units; the clause's `direction` orients them, MM-8), with the registered item set as the expected items. Per-item means over the repeats present in both arms are the analysis unit (05 §3.3, §3.6; `unit: item` since design revision 11, which resolves MM-GAP-10).
- **MM-8 Sign convention (05 §3.1:56).** Oriented score s′ = score for `higher_is_better`, s′ = −score for `lower_is_better`. Δ = mean(s′_candidate − s′_baseline), so **Δ > 0 always means the candidate is better**. The margin δ is registered in oriented units; superiority with δ = 0 is unaffected. The report shows `direction`, oriented Δ̂ and interval, and the natural-unit difference `candidate − baseline` with its interval (for lower-is-better: the oriented interval negated and its bounds swapped), each labelled.
- **Acceptance (MM-1 to MM-8):**
  - schema fixtures: each rule above has a refusing fixture (score and error both set, unknown key, seed ≠ registered seed, score out of range, direction mismatch, duplicate key); an item not in the set gives a MISSING `unknown_item` report (MM-6), not a refusal;
  - **WER fixture:** candidate WER lower on most items gives oriented Δ̂ > 0 and PASS; the mutant "no negation for lower-is-better" turns it into FAIL and must be killed;
  - **equivalence with Tier B:** converting the Tier B GSM8K fixture arms to `items.jsonl` (score = numeric_match reward) and running `ext-collect` gives a gate report whose statistics equal `tierb-collect`'s field by field;
  - merge fixtures for every refusal in MM-5.

## 1a. Constraint-evaluator records and recorded judge verdicts (design revisions 12 and 13)

Design: 05 §3.9 and §6.1 (a)-(e), 06 §9 and §12.1 (R12-1 to R12-5, R13-1 to R13-4). Tests: `tests/README.md` §11.17 (R12A-1 to R12A-17), `tests/test_r12_constraints.py`. The prototype never calls a judge model: a judge runs outside the gate (local model on the host GPU, or an external API under an egress approval), and the gate reads what it recorded. Field names follow the revision 11 per-item record (`item`, not `item_id`; the rename is section 11.16 of the tests README, implemented in `gatedtrain.items` and `gates.evaluate_items`).

- **MM-C1 Per-item record of the constraint evaluator.** One line of `items.jsonl` per (item, repeat), the 05 §3.8 shape with nothing added: `item`, `repeat`, `seed`, `score`, `error`, `sub_metrics`, `output_ref`. `score` is 1 when the output violates any registered constraint and 0 when it violates none (all checkers combined: tool results and judge verdicts); any other value is a missing item with reason `out_of_range`. `error` is `{class, message}` for evaluator failures; an unparseable judge response is `{class: unparseable_judge_response}`, a missing item, never a 0. `sub_metrics` may hold non-numeric values for constraint evaluators (an exception to MM-1's "finite numbers"): `violated` (list of constraint IDs), `per_constraint` (`{cID: 0 or 1}`), `rationale` (`{cID: text}`), and per judge call `request_hash` and `cache_hit`. They are descriptive and never decide. `output_ref` names the judged output.
- **MM-C2 Judge batches.** One line of `judge_batches.jsonl` per judged batch, in the same arm directory: `{batch, judge, records: [[item, repeat], ...], canaries: [{canary, flagged, request_hash}]}`. `judge` is a judge ID of the registered constraint set; `canary` is a registered canary ID; `flagged` is whether the judge reported the canary's violation. Canary outputs are not items and never enter v_i. Every record checked by a judge must be in exactly one batch of that judge; a batch whose `judge` is not a judge of the registered set, or a record in two batches of one judge, makes the clause MISSING (`malformed_batch`), and every judge on a blocking clause must cover all judged records with its own batches (tests README R12A-21). `flagged` counts only when it is `true`; an absent key is not flagged. For a judge that blocks a constraint clause alone (a judge on a blocking constraint clause; design revision 13, R13-4), a batch without a registered canary, or a judged record outside every batch, makes the clause MISSING (`canary_absent`), and a canary with `flagged: false` makes it MISSING (`canary_missed`). A supporting judge (non-blocking clause) needs no per-batch canaries: its batches and canary results are reported but never make the clause MISSING (06 B26 conformance canaries are outside the prototype).
- **MM-C3 Arm metadata.** `eval_meta.json` (MM-2) adds `constraint_set_hash`, the hash of the constraint set the evaluator ran with (R12A-3); a value other than the registered set's hash is MISSING (`evaluator_hash_mismatch`). It also records `model_manifest_hash`, the evaluated checkpoint's manifest hash (05 §3.8); with expected model hashes given, a different, null or absent value is MISSING (`model_hash_mismatch`, as `gates.evaluate_items`; R12A-19). For an external judge it also records `egress_approval_id`; the registration holds the approval (R12A-13), and a value other than the registered `approval_id`, null or absent is MISSING (`egress_unapproved`, R12A-23).
- **MM-C4 In memory.** `constraints.evaluate_constraint(clause, constraint_set, judge_qualification, candidate, baseline=None, *, items, min_paired=10, max_unpaired=0, expected_models=None)` takes each arm as `{records: [MM-C1 dicts], batches: [MM-C2 dicts], constraint_set_hash, model_manifest_hash, egress_approval_id}` (the last two from MM-C3). `items` is the registered item set and is required: the expected items are `items` × K per arm (05 §3.4; R12A-18), never the items found in the records. `expected_models` is `{candidate: hash, baseline: hash}` as in `gates.evaluate_items`. A tool-only constraint set has no batches.

## 2. Generic external-run collect

- **MM-9 Command.** `gatedtrain ext-collect <spec.yaml> --adapter NAME --stage-out DIR --launch-record FILE --smoke-record FILE --eval-baseline DIR --eval-candidate DIR [--runs-root R]`. It writes the same layout as `tierb-collect`: `registration/`, `plan`, `eval/<arm>/` (copies of `items.jsonl`, `eval_meta.json`, `merge.json`), `ledger/consumption.parquet`, `lineage/`, `manifests/`, `lockfile.json`, `report/`. `gatedtrain impact` works on it unchanged (plus MM-30). `--eval-baseline` and `--eval-candidate` take an arm from `ext-merge-eval` or `ext-from-nel` (with `merge.json`, checked against its sources) or one written in one piece by an evaluator (no `merge.json`; its provenance is the evaluator's claim, MM-5).
- **MM-10 Refuse before writing.** As H-6: every check of MM-3 to MM-8, MM-11 and the adapter's checks runs first; any problem exits 3 with rule, field and fix, and creates nothing. Exception: an item outside the registered set is not refused; the gate reports MISSING `unknown_item` (MM-6, 05 §3.8).
- **MM-11 Generic part (one implementation, all adapters):** spec and registration loading and pins (`check_pins`); registration hash; item set hash; arm schema, merge provenance and pairing; the revision 10 gate checks; launch record policy (MM-34) and GPU-hour accounting (MM-36); smoke record presence and verdict (MM-38); manifests, lockfile skeleton, lineage files, report, tags; exact-text overlap between item set payloads and training shards (count reported as `contamination: exact_overlap=<n>`, refused when n > 0 unless the registration sets `contamination.allow_exact_overlap: true`).
- **MM-12 Adapter part.** An adapter is a pure-Python class (originally `gatedtrain/ext/adapters/<name>.py`; now a recipe package's module, registered through the entry point group `gatedtrain.adapters`) that imports no framework, torch or pickle loader. It reads JSON, YAML, text logs and safetensors headers, and hashes everything else. Interface:

  | Member | Returns |
  |---|---|
  | `trainer_id`, `evaluator_ids` | Spec `uses` and gate `evaluator` values it accepts |
  | `metric(evaluator_id)` | Name, direction, range, score/error classification (MM-3, MM-4), scorer identity |
  | `find_cuts(stage_out)` | Ordered `(last_step_included, path)` of complete checkpoints; a directory missing its completeness marker (MM-20) is reported as incomplete, never used |
  | `identity(cut, base)` | `model_hash`, `cut_hash`, components and base reference (§3) |
  | `consumption(stage_out, data, cuts)` | Ledger rows and the precision actually achieved (§4) |
  | `framework_identity(stage_out, launch)` | Pins read from the run's own outputs, compared with the launch record (MM-33) |
  | `checks(...)` | Adapter-specific refusals (profile, base model, normalizer) |

- **MM-13 Spec ids.** Spec and registration accept the trainer and evaluator ids of the adapter registry (§6) only; Tier A and Tier B behaviour and ids are unchanged. `rl.nemo_rl@0.1` stays with `tierb-collect`; area 6 uses the `nemo_rl_ext` adapter and area 7 its sibling `nemo_rl_vlm` (row 7 deviations), which reuse `ledger.py` and the Tier B stage checks.
- **MM-14 Lockfile.** `backend.trainer` and `backend.evaluator` come from the adapter and the launch record: runtime kind, image ID, venv lock hash, freeze hash, framework name, version and commit, recipe and profile. Added top-level fields: `adapter`, `direction`, `gpu_seconds` (MM-36), `smoke_record_sha256`, `independence_tier` (MM-16).
- **MM-15 Two-stage areas.** Area 6 (SFT then GRPO) is two `ext-collect` runs; the GRPO spec's baseline `model` is the SFT run's trained checkpoint, and its manifest hash must equal the SFT run's `model_hash` (refused otherwise), which gives the lineage chain for MM-30.
- **MM-16 Independence tier in the report.** Each adapter registry entry declares, per evaluator, whether the scorer is a training reward or shares its tool or backbone (05 §6.1:223). The report prints the tier (T0 when the scorer is the training reward), and a T0 deciding metric prints "non-blocking under 05 §6.1; prototype plumbing only" beside the status.
- **Acceptance:** an end-to-end fixture per adapter (recorded-shape outputs, two arms) ends in a run directory and a report; a fixture with one incomplete checkpoint directory refuses only if it is the last one; the parent-directory regression of H-6 holds for `--eval-*` and `--stage-out`; a spec naming an unregistered id is refused at validation with rule, field and fix.

## 3. Checkpoint identity

- **MM-17 Two hashes per cut.** `cut_hash` is the manifest hash (canonical JSON per RFC 8785) of every file of the checkpoint directory (resume state included). `model_hash` is the manifest hash of the **deployable components only**: weights, model config, tokenizer or processor files, generation config, normalizer statistics, and the base reference for LoRA. Lineage rows and the impact answer carry both; the gate's evaluated checkpoint is a `model_hash` (MM-GAP-8).
- **MM-18 LoRA.** For adapter-only checkpoints the components are the adapter weights and adapter config. `base_ref = {repo, revision (40-hex commit), manifest_hash of the local plain base directory}`; `model_hash = sha256(canonical_json({base: base_hash, adapter: adapter_hash}))`. The lineage writes a `lora_compose` activity that `used` the base and the adapter and generated `model_hash`, without writing merged weights (MM-GAP-7). The baseline arm of a LoRA run evaluates the base alone, with `eval_meta.checkpoint` equal to the base hash. A base revision that is a branch name, not a commit, is refused.
- **MM-19 Embodied state.** For areas 4 and 8 the normalizer statistics (SB3 `VecNormalize` file; LeRobot normalization buffers or processor state, location unverified) are model components (08 §6.2). Each arm's `normalizer_sha256` must equal the normalizer in the evaluated checkpoint; a missing or different normalizer refuses. `env_version` (08 §6.1:314) is a `used` input of the stage and of the gate, recorded in `env_version.json` (`{package, version or commit, env_id, env_kwargs, assets_manifest_hash}`), and the gate's `env_version_sha256` must equal the registered evaluation environment.
- **MM-20 Completeness markers** (per adapter, verified in the smoke output): the cut is used only when every listed component exists and the framework's last-written file is present (for example `trainer_state.json` for HF Trainer and TRL). The base model directory must be plain, without symlinks or `.cache/` (Tier B LOW-4). Exception (row 2b, decision "Area 5 decisions"): an adapter may declare top-level directory names its base hash leaves out (`base_excludes`; `flow_grpo_sd35`: `.cache`); such a name, when present, must itself be a plain directory, never a symbolic link or a file (else refused, `EXT-BASE`), so the no-symlink rule of manifest rule H2 holds for the walked base; whatever lies inside it is neither walked nor hashed, and a `.cache` below the top level is hashed as usual.
- **MM-21 Base binding.** The adapter checks that the cut names the registered base: HF `config.json` `_name_or_path` or `adapter_config.json` `base_model_name_or_path` resolves to the spec's `model` artifact, by local path or by the recorded `{repo, revision}`; a mismatch refuses (as `_check_base_model`). For TRL area 1 the reference is `run_args.json` `model_name_or_path`: transformers 5.17.0 never writes `_name_or_path` into `config.json` (configuration_utils.py:1068-1069; tests/README.md EXT-20). **Data binding, symmetric (EXT-65):** the launch record has a read-only mount whose host path resolves to the spec's export directory (the parent of the training shards, holding the concatenation `train.jsonl`); `run_args.json` `train_file` is that mount's `<container path>/train.jsonl`, and `train_file_sha256` is present and equals the SHA-256 of the spec's shards concatenated in file-name order. A missing `run_args.json`, a missing or different hash, or another path refuses (`EXT-DATA`): a run on another training file can neither be ledgered nor checked for contamination against the spec's data. `ext-launch --spec` checks both mounts at launch.
- **Acceptance:** fixtures for each adapter's component list; a LoRA fixture whose base revision changes gives a different `model_hash` with the same adapter hash; an SB3 fixture evaluated with another run's `VecNormalize` file refuses; a resume-state-only edit (optimizer file) changes `cut_hash` but not `model_hash`.

## 4. Consumption records

Rows keep the `ledger.py` schema (05 §12.2). Precision follows 05 §11.2; each adapter records the precision it **observed**, never one it infers from a seed or replay (MM-GAP-6).

- **MM-22 Dataset trainers, sequential order known** (NeMo RL areas 6 and 7 with `data.shuffle=false` and a `gatedtrain` shard export): precision `iteration` from the trainer's own step logs, exactly as Tier B (`ledger.py`, G-1, G-7).
- **MM-23 Dataset trainers, random order** (TRL, HF Seq2SeqTrainer, LeRobot): precision `stage` unless the run writes an observed sample log (MM-26). A `stage` edge has no ledger rows; the impact query returns every checkpoint the stage generated with answer "possibly consumed" and precision `stage` (MM-GAP-5). TRL with dataset shuffling disabled (`GRPOConfig.shuffle_dataset=False`, trl 1.16.0 grpo_config.py:507-510, trainer/utils.py:935) may reach `iteration` through MM-22's shard mapping; the adapter claims it only when the run's saved config (`run_args.json`) shows it (tests/README.md EXT-48, EXT-49).
- **MM-24 Diffusion (areas 2a, 2b, 3).** The prompt file is exported to shards (`prompts` disjoint from training prompts). The target precision is `row`: one record per generated sample with `data_ref.row = sha256(prompt_id)`, `seed_inputs.seed`, `step`, and `sample_id = H(run, attempt, epoch, step, prompt_id, seed, member)`, from an observed log `samples.jsonl` with `(prompt_id, seed, epoch, step)` per sample. Without that log: `stage`. flow_grpo's sampler repeats prompts by seed; the log must still be written at sampling time, not reconstructed.
- **MM-25 Environment RL (area 4).** No dataset. The adapter materializes an **environment snapshot** directory (MM-GAP-4): `env_version.json`, one shard file per `env_params_version` (randomization ranges, task kwargs), and `train_seeds.json` (the vector-env base seed and the number of environments). Rows: precision `iteration`, one per (PPO iteration, `env_params_version` shard), `derivation: observed`, with `step` = iteration index and `data_ref` = the snapshot's manifest hash and the shard; as 05 §12.2 requires for an `iteration` record, `data_ref.row`, `sample_id`, `chunk`, `rewards` and `seed_inputs` are null and `outcome` is `consumed`. The chunk ranges (cumulative environment steps of each iteration) and the per-episode data (env, episode, seed, initial state, payload, steps) stay in the runtime's own consumption log (`rollouts.jsonl`, written at each rollout's end; SB3's logger is not read) and never enter the ledger (review round 7: this item named `chunk` and `seed_inputs.seed`, which contradicted 05 §12.2; EXT-102). Impact on an env-params shard returns checkpoints at or after the first iteration that used it.
- **MM-26 LeRobot (area 8).** Default: `stage`, with `data_ref.snapshot` = the dataset manifest at its pinned Hugging Face revision ("possibly consumed": the whole revision). Optional `row`: an observed log of `(episode_index, frame_index)` per batch written at load time; `data_ref.row = sha256(episode_index, frame_index)`, shard = episode file.
- **MM-27 Observed sample logs.** A sample log (MM-23, MM-24, MM-26) is written by a launcher-side wrapper entry point that wraps the framework's sampler or dataset object at run time; it never edits framework source. Lines are `{step, epoch, key fields}`; the adapter refuses a log whose per-step counts disagree with the checkpoint's recorded sample count, and accepts records only up to each cut's `last_step_included` (later ones are orphaned, counted in the report).
- **MM-28 Exposure.** Rows whose samples were generated but dropped (zero-advantage groups, filtered episodes) are written with outcome `filtered` only when the framework logs them; otherwise the report says `exposed: not recorded`.
- **MM-29 Seeds.** Every run records its training seed and the derivation it uses; 05 §14's H(run_seed, step, data_ref, sample_index) is not claimed for any framework here.
- **MM-30 Transitive impact.** `gatedtrain impact` follows `used` model edges across run directories under `--runs-root`: when run Y's baseline or initial model hash equals a checkpoint that possibly consumed S, Y's generated checkpoints are returned too, with the coarsest precision on the path (05 §11.2, §11.3).
- **Acceptance:** per adapter, an impact query on a used shard returns the trained checkpoint with the expected precision and answer, an unused shard returns nothing, and the baseline is never returned; a sample log with one step missing refuses; area 6's chain returns the GRPO checkpoint for a shard consumed only by SFT, with precision the coarser of the two edges.

## 5. Launcher contract

- **MM-31 One wrapper.** Every GPU process runs through `<HOST_WORK>/bin/gpu-step.sh <label> <docker run args>` on `docker --context gatedtrain`, with `GATEDTRAIN_GPU_CAP_H=1000` (a budget ceiling high enough not to limit runs; GPU hours are still logged and every full run is preceded by a smoke), `GATEDTRAIN_GPU_USED_H` from `gpu-log.md`, and `GATEDTRAIN_GPU_STEP_EST_H` from the smoke record. `gatedtrain ext-launch --adapter NAME --profile smoke|full ... --out-record FILE` writes the launch record and prints the exact command; it never runs it. CPU-only steps (downloads, SB3 if it runs on CPU) use the same command shape without `--gpus` and are logged with 0 GPU-hours.
- **MM-32 Runtime pinning.** Two kinds only:
  - `container`: the image by ID (`sha256:...`, from `docker image inspect`) or a digest reference, never a mutable tag alone;
  - `venv_in_container`: a CUDA runtime base image pinned as above, plus a host venv built from a committed lock (`uv.lock` or a hashed requirements file) and mounted read-only. The record holds the lock's SHA-256.
- **MM-33 Framework pin.** A pre-step inside the same runtime writes `<out>/env-freeze.txt` (package list with versions; for source checkouts the commit). The adapter checks that the framework version or commit in the freeze equals the launch record's, and the lockfile records the freeze hash.
- **MM-34 Narrow mounts and isolation.** `ext-collect` refuses a launch record that breaks any rule:
  - inputs (base model, data export, item set, config, code, HF cache) mounted read-only;
  - exactly one read-write mount: the run's own new output directory, which equals `--stage-out` (or the arm directory for evaluation); it resolves (strict `realpath`) to a directory strictly under the configured output root (`<output-root>`, recorded as `output_root`), outside `<HOST_WORK>`, owned by the container's uid, and empty at `ext-launch` and `--recheck` (EXT-63); at `ext-collect` every file of the collected cuts and `run_args.json`, `env-freeze.txt`, `samples.jsonl` postdates the label's first `START` (EXT-64); plus tmpfs scratch, mounted `rw,exec,nosuid,nodev,size=8g`: `exec` because Triton and torch.compile load compiled objects from their caches under `/tmp`, and Docker's tmpfs default is `noexec`; `nosuid,nodev` as the area-1 README (area-1 runtime, `<mm-root>/area1-trl/README.md`); the printed command also adds `--shm-size=8g` and, for GPU steps, `--runtime=nvidia` (tests/README.md EXT-24);

## 7. Smoke checks before each full run

- **MM-38 Smoke record.** Before an area's full run, a smoke run (5-10 minutes, estimate) and a 20-item evaluation of the baseline write `smoke.json`: peak GPU memory (from `nvidia-smi --query-gpu=memory.used` sampling every 5 s), host RAM and swap peak, seconds per training step, projected full-run GPU-hours, baseline item scores, and error count. Verdict PASS only if:
  - peak GPU memory ≤ 22.5 GB (of 24.5 GB);
  - projected GPU-hours plus `gpu-log.md`'s total stays within the budget ceiling (`GPU_CAP_H`, 1000 GPU-hours);
  - zero evaluator errors;
  - the baseline is not degenerate: for a bounded metric the mean lies strictly inside the range by at least 5% of its width, and for every metric fewer than 50% of item scores share one value and the item standard deviation is non-zero (G-21 lesson; 05 §6.1:233 floor and ceiling rule). For a binary metric (registry `binary: true`) neither the 5 % rule nor the "fewer than 50 % share one value" rule applies; such a baseline is degenerate only when its mean is 0 or 1 (all scores at one bound) (maintainers' decision 2026-11-11, tests/README.md EXT-29). Design revision 18 (R18-8, option B): for a non-binary metric, scores exactly on the finite bound at the metric's best end (the lower bound if lower is better, the upper bound if higher is better) cannot be the value that makes up 50% (still a share of the whole sample); a score on the worst end counts as before; fewer than a quarter of the scores (at least 2) off that best bound is degenerate (`degenerate_bound`); a sample with no score on the best bound is judged as before. With several clauses the record carries `baseline_scores_by_evaluator` and every clause's evaluator is checked with its own row.
- **MM-39** A FAIL verdict stops the area: it is reported and the full run is not started. `ext-collect` refuses without a PASS smoke record for the same adapter, base `model_hash` and item set hash.
- **Acceptance:** smoke-record fixtures for each failing condition refuse; a baseline fixture with all-zero scores is reported degenerate.

## 8. Design gaps

Each entry: what the design lacks, citation, proposed fix. The prototype applies the fix locally and records it as a design gap; design changes follow DA3-4 (design.md, "Records").

- **MM-GAP-1 No per-item record schema for non-text outputs.** 05 §3.8 `evaluate` takes "paired per-item records (prompt, sample, seed)" and reuses NeMo Evaluator `results.jsonl`, which is text-centric. **Fix:** package A defines `ItemEvalRecord` (MM-1, MM-2), with `output_ref` for images, video, audio and CAD, and NeMo Evaluator output converted into it.
- **MM-GAP-2 Lower-is-better metrics are only half specified.** 05 §3.1:56 negates them, but the registration (§3.7:155) has no direction field and does not say whether the margin is in natural or oriented units or how the report shows the sign. **Fix:** `clause.direction` in the registration, margin in oriented units, report both forms (MM-8).
- **MM-GAP-3 No declared score range.** The [0, 1] range check is a prototype decision (D-11); the evaluator manifest (05 §6.1:233) declares none. **Fix:** the evaluator manifest declares `score_range`; out-of-range records are MISSING.
- **MM-GAP-4 Consumption for environment-based RL.** `data_ref` needs a snapshot and shard (05 §12.1:381), while 08 §6.1:315 makes `env_params_version` per-row data and 08 §2.4:75 gives wrapped libraries no consumption records. Env seeds and parameter versions have no lineage entity. **Fix:** an `EnvSnapshot` entity (`env_version`, one shard per `env_params_version`, seed ranges) usable as `data_ref.snapshot`, with `row = H(episode seed)` when episodes are logged.
- **MM-GAP-5 `stage` precision has no query rule.** 05 §11.2:363 lists `stage`, but §12.2:396 allows ledger records of `row`, `step_range` and `iteration` only, and §11.3 decides membership by first-step rollups that a `stage` edge lacks. **Fix:** a `stage` edge makes every checkpoint the stage generated "possibly consumed" (MM-23).
- **MM-GAP-6 Observed versus reconstructed consumption.** Deterministic samplers (flow_grpo's seeded prompt repeat) allow reconstruction, and 05 §14:488 even derives seeds by formula, but §11.2 does not say whether reconstructed records may claim `row`. **Fix:** a `derivation: observed | reconstructed` field; reconstructed records are capped at `iteration` unless a replay conformance test proves them.
- **MM-GAP-7 Unmerged LoRA identity.** 05 §11.1:351 covers LoRA merges only; the `Checkpoint` entity (05 §11) has no base reference, yet LoRA adapters are evaluated and served unmerged. **Fix:** `Checkpoint.base_ref` plus a composed model identity H(base, adapter) and a `lora_compose` activity (MM-18).
- **MM-GAP-8 Deployable model hash versus cut hash.** 02 §2.4:109 hashes every component of a cut, resume state included; 05 has no hash of the deployable subset, so "the evaluated checkpoint" is ambiguous and optimizer-only differences change it. **Fix:** `Checkpoint.model_manifest_hash` over weights, config, tokenizer or processor, normalizer and base reference (MM-17).
- **MM-GAP-9 Normalizer binding at evaluation.** 08 §6.2 makes normalizer statistics policy state carried in cuts and exports, but no rule ties a gate's evaluation to the checkpoint's normalizer. **Fix:** evaluation records name the normalizer hash; a mismatch is MISSING (MM-19).
- **MM-GAP-10 The analysis unit "prompt" does not fit every family.** 05 §3.3:100 and the clause's `unit: prompt` assume prompts; here the items are utterances, episode seeds and `(task, init_state)` pairs, and 08 §6.1:318 wants a fixed evaluation distribution declared in the gate spec, while 05 §3.7:155 registers only a prompt-set hash. **Fix:** rename the unit to `item`, defined per family, and register `eval_distribution` (`item_set_hash`, plus `env_version` and `env_params_version` for environments).
- **MM-GAP-11 Scorer validity for learned continuous scorers.** 05 §6.1:233 measures false-positive and false-negative rates against a reference judgment, which does not apply to aesthetic predictors, PickScore or OCR confidence; when the scorer is also the training reward it is T0 (:223) and cannot block. **Fix:** for continuous learned scorers, validity is rank agreement with a T2 or T4 reference on a labelled baseline sample, plus the §6.2 transfer test; until then such gates are non-blocking and reported as T0 or T1 (MM-16).
- **MM-GAP-12 Code-executing CAD environment is blocked.** 06 B18 (:185) and §10 (:343-344) block environments that execute model output until the P8 sandbox, in every profile; the controlled prototype exception (design R10-11) does not name B18 among its exceptions. **Fix needed before area 6:** a maintainers' decision that either allows a prototype-local sandbox (MM-34 plus read-only root filesystem, `--memory`, `--pids-limit`, per-call timeout and address-space limit) as a recorded B18 deviation, or drops area 6. **Stop condition:** area 6 does not start without that decision. **Resolved (maintainers' decision 2026-11-13, "Area 6 decisions"):** a prototype-local sandbox as a recorded B18 deviation: one forked process per program with rlimits and a wall-clock kill inside the executor container (`--network none`, non-root, no capabilities, no-new-privileges, read-only root, CPU / memory / pids limits), launched by `ext-launch` as the GRPO run's paired sidecar and as the scoring step (row 6 deviations).
- **MM-GAP-13 Ratio metrics.** Corpus WER is a ratio of sums; 05 §3.4 covers per-prompt means, binary rates and win rates only. **Fix:** allow a registered ratio-of-sums estimator with a cluster bootstrap over items, or require the registration to name the per-item mean as the deciding metric (the prototype does the latter).
- **MM-GAP-14 Checkpoint completeness for wrapped libraries.** 08 §2.4:69-73 expects the adapter to write a cut manifest after each library checkpoint, and 05 §12.4:424 excludes records not covered by a committed cut, but nothing says how an adapter knows a library checkpoint is complete. **Fix:** each adapter declares a completeness marker per library and version (MM-20), checked by the conformance kit.
